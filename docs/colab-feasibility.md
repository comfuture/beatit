# Colab GPU 실행 검토 — 2026-10-26

Colab T4는 초기 준비 비용을 포함해도 이 파이프라인을 가속할 수 있다.
로컬 Mac과 ARM64 Docker에서 공식 Colab CLI로 실제 변환과 결과 회수를 검증했다.
현재 chunsik 웹 앱의 작업 큐에 자동 연결한 상태는 아니며, 기존 CPU 서비스는 유지된다.

## 실측

코드는 `8d5f96b776276cbd0f8d3dc90b313a5aa51e7f12`, Python 3.12,
PyTorch 2.8.0, CUDA wheel은 12.8이다. Colab 기본 Python 3.13 / PyTorch 2.11 환경을
그대로 사용하지 않고 `uv.lock`에 맞는 별도 가상환경을 설치했다. 모든 모델은 Colab에서
공개 저장소로부터 내려받았으며, GitHub/Hugging Face 토큰이나 Drive 마운트는 사용하지 않았다.

| 입력 / 실행 조건 | 시간 |
| --- | ---: |
| 12초, chunsik ARM CPU 2코어 상한 | 290.3초 |
| 동일 12초, T4 첫 변환, 준비 시간 별도 | 39.9초 |
| 동일 12초, 같은 런타임 재사용 | 15.4초 |
| 4분 35초 전체 곡, 준비된 T4 런타임 | 103.8초 |
| 4분 35초 전체 곡, 새 런타임 + Docker, 할당부터 결과 회수까지 | **248.1초 (4분 8초)** |

마지막 행은 별도의 새 런타임에서 전체 곡을 첫 작업으로 실행한 연속 측정이다.
런타임 해제까지 포함하면 249.9초다. 사전에 만들어 둔 CLI Docker 이미지 빌드와
로컬 소스 tar 생성 시간은 포함하지 않는다. 프런트엔드 빌드는 추론에 필요하지 않다.

| --- | ---: |
| T4 할당 | 3.8초 |
| 코드 + 4.1 MB 입력 전송 | 4.8초 |
| 환경 준비 명령 전체 | 99.8초 |

| 위 준비 중 모델 다운로드 | 22.4초 |
| 변환 실행 명령 전체 | 136.9초 |
| 위 실행 중 파이프라인 자체 | 131.1초 |
| 결과 다운로드 | 1.6초 |

준비된 런타임의 재실행은 새 프로세스에서 수행했다. 따라서 15.4초 및 103.8초 수치는
모델 객체를 GPU 메모리에 계속 유지한 결과가 아니라, 같은 VM의 설치 환경·다운로드·컴파일
캐시를 재사용한 결과다. 최대 측정 GPU 메모리는 약 1.56 GiB였다.

MusicXML/SVG XML 파싱, MIDI 헤더, ZIP CRC와 CUDA 사용을 확인했다. 전체 곡 출력은 SVG
3페이지다. CPU/GPU 및 반복 실행의 검출 이벤트가 완전히 같지는 않았으며, 이 실험은
음악적 정확도나 CPU/GPU 결과 동등성을 검증하지 않는다. 전체 곡의 chunsik CPU 시간은
직접 측정하지 않았으므로, 기존 1시간 이상 예상과의 배수 비교는 실측으로 제시하지 않는다.
CPU 12초 기준은 스레드 설정 수정 전 실행이며, 별도 동일 청크 비교에서 4/2 스레드는
45.419/45.543초로 관측 가능한 개선이 없었다.

원시 수치의 공개 가능한 요약은 [JSON](benchmarks/colab-2026-10-26.json)에 있다.
테스트 런타임 두 개는 모두 해제했으며 임시 인증 상태 파일도 제거했다.

## 준비된 런타임 재사용

운영에서는 매 작업마다 `colab run` 또는 `colab new`를 실행하지 않는다.
우선 최대 한 개의 명시적으로 관리하는 T4 런타임에 작업을 순차 전달한다.

1. 컨트롤러가 실제 할당 상태와 준비 버전을 조회한다. 정상 런타임이 있으면 명시적인
   세션 이름으로 `colab exec -s ...`를 호출한다. 회수되었을 때만 새로 할당한다.
2. 준비 버전은 코드 SHA, `uv.lock` 해시, Python/PyTorch/CUDA 버전, 모델 체크섬으로
   판단한다. 버전이 같으면 소스 업로드, 의존성 설치, 모델 다운로드를 생략한다.
   버전이 바뀌면 새 환경을 준비하고 준비 상태를 확인한 후 새 작업을 받는다.
3. 작업은 별도 UUID 디렉토리와 프로세스로 실행한다. 영구 결과를 DB/객체 저장소에
   반영한 뒤 해당 작업의 원본·임시 파일을 정리하고 환경·모델 캐시만 남긴다.
   프로젝트 소유권 검사는 [멀티유저 이슈 #7](https://github.com/comfuture/beatit/issues/7)의
   인증·권한 계층에서 수행해야 한다.
4. 연속 작업은 런타임을 재사용하고, 대기 작업이 없으면 설정 가능한 유휴 유예 시간
   (초기 제안: 10분) 후 해제한다. Colab이 더 일찍 회수할 수 있으므로 준비 상태는
   보장값이 아니라 매번 확인하는 상태다. 인위적인 무한 keep-alive를 사용하지 않는다.
5. DB의 런타임/작업 lease로 중복 실행을 막고, 런타임 소실 시 재할당·재시도한다.
   모델을 메모리에 상주시켜 추가로 단축하는 방법은 이후 별도 정확도·메모리 검증 대상으로 둔다.

이번에 추가한 `benchmark_colab.py`는 초기 비용을 재기 위해 **의도적으로 매번 새 런타임을
생성하는 벤치마크 도구**다. 위 재사용 컨트롤러를 구현한 도구로 간주하면 안 된다.

## 노트북 문서 증식 방지

일반 작업은 `.py` 파일을 `colab exec`로 실행한다. `.ipynb`를 생성하거나 Drive로
복사할 필요가 없다. CLI의 할당 코드에 있는 `notebook_hash`는 런타임 요청 식별자이며,
확인한 클라이언트 경로는 Colab 할당 API를 사용한다. `.ipynb` 입출력 및 명시적인
`colab log -o ...ipynb` 내보내기는 일반 작업 경로에서 사용하지 않는다.

설치된 0.7.4 소스에서 `.py` 실행과 `.ipynb` 파일 실행을 구분하며, `_output.ipynb`
쓰기는 후자에서만 실행됨을 확인했다. 이 검증에서 Drive 생성/마운트 명령은 호출하지 않았다.
로그는 프로젝트/작업 ID에 따라 Beatit 저장소에 모으고 보존 정책을 적용한다.
재시도는 동일 작업의 시도 기록을 추가하며 새 Colab 문서를 만들지 않는다.

## 최소 인증과 Docker

검증한 경로는 다음과 같다.

```text
로컬 컨트롤러: 기존 Colab OAuth로 GPU 할당·해제
    → 해당 런타임의 임시 상태/프록시 토큰
    → ARM64 Docker CLI: 업로드·설치·GPU 실행·다운로드
```

Docker에는 Google OAuth `token.json`, refresh token, gcloud 설정, 서비스 계정 키,
Drive 인증을 넣지 않았다. `--auth adc`를 명시하고 ADC 자체가 없는 컨테이너에서도,
유효한 런타임 토큰만으로 전체 작업이 성공했다. 이미지에도 인증 파일이 포함되지 않는다.
토큰은 해당 VM의 코드 실행·파일 접근 권한이므로 비밀로 관리해야 한다.

상태 JSON을 읽기 전용으로 직접 지정하면 CLI의 옆 `.lock` 파일 생성이 실패한다.
읽기 전용 secret은 임시 쓰기 가능 상태 경로에 복사하거나, 0700 작업 디렉토리 안의
0600 런타임 상태 파일을 사용한다. 제공한 컨테이너는 일반 사용자, 읽기 전용 루트,
임시 HOME을 사용한다. 기본 CLI의 디버그 로그에도 토큰이 남을 수 있으므로 HOME은
외부 공개 디렉토리에 두지 않는다. 벤치마크 컨테이너의 HOME은 종료 시 폐기한다.

임시 프록시 토큰은 이 실험에서 약 1시간 수명으로 발급됐다. CLI는 만료 5분 전부터
계정 인증으로 갱신하므로 토큰만 받은 컨테이너가 무기한 독립 실행할 수는 없다.
운영 컨트롤러가 갱신/할당/해제를 담당하고 작업 컨테이너에는 최신 임시 토큰만 제공하는
구조가 적합하다. 서버가 독립적으로 할당까지 수행하려면 별도 컨트롤러에 계정 OAuth
갱신 자격 증명을 안전하게 제공하는 단계가 추가로 필요하다. 그 서버 배포는 아직 검증하지 않았다.

기존 CLI OAuth의 기본 요청 범위에는 Colab 외에 `cloud-platform`과 `drive.file`도 있다.
그 파일 전체를 웹 앱/작업 컨테이너에 복사하는 방식은 최소 권한 방식으로 간주하지 않는다.
서비스 계정이 개인 Colab GPU 이용 권한을 대체한다고도 가정하지 않는다.

## 재현

기존 로컬 Colab CLI 인증이 필요하다. GPU는 할당 가능 여부와 계정 한도에 영향을 받는다.
아래 도구는 실패 시에도 자신이 생성한 런타임을 해제하도록 구성했다.

```sh
docker build -f deploy/colab/Dockerfile -t beatit-colab-cli:probe .
python3 scripts/benchmark_colab.py \
  --input /absolute/path/to/audio-or-video \
  --work-dir work/colab-probe-unique-name \
  --docker-image beatit-colab-cli:probe
```

`report.json`, 단계별 로그, 검증된 `results.zip`을 지정한 작업 디렉토리에 저장한다.
작업 디렉토리는 새 경로여야 하며 비공개로 유지한다. 공개 Git 저장소로 올리지 않는다.

## 운영 판단과 근거

실측상 Colab GPU 오프로딩은 가능성이 충분하며, 런타임 재사용으로 초기 준비 약 100초를
대부분 피할 수 있다. 다만 Google은 리소스/수명을 보장하지 않으며 무료·잔액 없는 런타임의
분산 워커 및 웹 UI 중심 사용을 제한한다. 현재 테스트 계정 잔액은 0이었고 T4 실험은
성공했지만, 이를 무인 멀티유저 웹 서비스의 운영 허가나 공급 보장으로 해석하면 안 된다.
운영 도입 시 해당 사용 방식에 맞는 유료 잔액/플랜과 장애 대응을 먼저 확인해야 한다.
